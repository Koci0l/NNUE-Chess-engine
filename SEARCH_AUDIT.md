# Search / engine audit — Kociolek 2.3

You asked why the engine's eval "jumps all over the place", why it sometimes plays a
move that does not match what it searched, and why the LMR values that came out of
SPSA look weird. The short answer: **the search was running with undefined behaviour
in the LMR condition, so the reduction it applied was effectively random.** There were
also two crash/corruption bugs, one of which makes every AVX2/AVX-512 build read
misaligned SIMD data.

Everything below was reproduced and re-tested on this checkout. Builds used
`-std=c++17 -O3 -march=x86-64-v3 -DNDEBUG -pthread` (LTO off only because the audit
sandbox has 4 GB RAM and `-flto=auto` gets OOM-killed here, not because of a code issue).

---

## 1. `givesCheck()` was evaluated *after* the move was made (UB, critical)

`src/search.cpp`, `alphaBeta()`:

```cpp
int check_cache = -1;
auto givesCheck = [&]() -> bool {
    if (in_check || !is_quiet) return false;
    if (check_cache < 0)
        check_cache = (board.givesCheck(move) != chess::CheckType::NO_CHECK) ? 1 : 0;
    return check_cache == 1;
};
...
board.makeMove(move);                        // <-- move applied here
...
bool can_reduce = ... && !givesCheck();      // <-- and queried here
```

The lambda caches its answer, so it is correct **only if something already called it
before `makeMove()`**. That was true when futility pruning ran, but futility pruning is
skipped in PV nodes, for the TT move, at `depth > 7`, near mate scores, and during
singular verification. In all those cases `can_reduce` ended up calling
`board.givesCheck(move)` on the *child* position, where `move.from()` is now empty (or
contains a different piece). `chess.hpp` computes the check bitboards from that square,
so the returned value is garbage — and in a debug build it fires the assert

```
chess.hpp:3162: chess::Board::givesCheck: Assertion `at(m.from()).color() == stm_' failed
```

Consequences:

* LMR was applied or skipped at random in exactly the nodes that matter (PV nodes),
  which is what makes the score wobble between iterations and between searches.
* It is plain undefined behaviour: reading `at(square)` for a square that no longer
  holds that piece, plus magic-bitboard lookups with a bogus occupancy.

**Fix:** evaluate `givesCheck` once, before the move is made, and use the cached bool
in both the futility condition and the LMR condition.

**This is almost certainly also what poisoned your SPSA run.** The tuner was fitting a
reduction formula whose decision was random in PV nodes, so it "fixed" the resulting
loss by pushing the coefficients somewhere strange. Re-tune LMR *after* this fix.

## 2. The SIMD alignment macros were misspelled → misaligned aligned loads

`src/accumulator.h` and `src/nnue.h`:

```cpp
#if defined(AVX512F)      // never defined by the compiler
#define ALIGNMENT alignas(64)
#elif defined(AVX2) || defined(AVX)   // never defined either
#define ALIGNMENT alignas(32)
#else
#define ALIGNMENT alignas(16)
#endif
```

GCC/Clang define `__AVX512F__`, `__AVX2__`, `__AVX__` — the version without
underscores is never set, so the fallback `alignas(16)` was always taken. But the
inference code uses `_mm512_load_si512` / `_mm256_load_si256`, which require 64/32 byte
alignment.

* `-march=native` on an AVX-512 machine: **SIGSEGV on the first evaluation**
  (reproduced here: `position startpos moves e2e4` + `eval` died inside
  `NNUE::vectorizedSCReLU`). `Accumulator` lives inside `ThreadInfo`, i.e. on the
  stack, so its address is only 16-byte aligned.
* `-march=x86-64-v3` (your Makefile): the *global* weight arrays happened to be
  32-byte aligned, so it worked on this machine; the accumulator alignment depended on
  the stack layout. That is the kind of bug that "works" until it does not, and it can
  also silently produce wrong numbers.

**Fix:** `alignas(64)` unconditionally (the `Accumulator` is 2048 bytes, so the padding
is free).

## 3. Castling was treated as a losing capture

Castling is encoded as *king takes own rook*, so `board.at(move.to()) != Piece::NONE`
is true for it. The code used that test as "is a capture" everywhere, so castling:

* was sorted into the capture list with `victim = 500` (own rook) and
  `attacker = 20000` (own king) → `SEE < 0` → pushed into `BAD_CAPTURES`, i.e. searched
  **last**, after every quiet move;
* was never treated as a quiet move (no LMR/futility bookkeeping, wrong `is_quiet` in
  the root, wrong `isQuietMove()` in the PV-history update);
* wrote garbage into the capture history (`g_captureHistory.update(KING, to, ROOK, …)`);
* could even be generated by the quiescence picker.

**Fix:** `isCaptureMove()` / `isPromotionMove()` / `isQuietMove()` helpers in
`src/types.h` that special-case `Move::CASTLING`, used by the move picker, quiescence,
the root ordering and `extractCaptureInfo()`.

## 4. Accumulator stack could overrun (`MAX_DEPTH = 128`)

`AccumulatorStack::push()` had no bounds check and `MAX_DEPTH` was 128 while the search
needs one entry per ply *plus one extra* for the singular-extension verification search,
which runs at the same ply as its node (MAX_PLY is 100). Long forcing lines with singular
extensions could push past the end of the array and overwrite the neighbouring fields of
`ThreadInfo` — silent memory corruption that would look like random blunders.

**Fix:** `MAX_DEPTH = 256` plus a bounds check in `push()`.

## 5. Hidden one-ply reduction ("IID reduction")

`src/search.cpp` reduced `depth` by one at every non-PV node that had no TT move:

```cpp
// IID reduction when no TT move
if (!in_singular_search && !is_pv_node && depth >= 4 && tt_move == chess::Move() && !in_check)
    depth--;
```

That is not IID, it is a silent extra reduction applied to a large fraction of all
nodes (and the reduced depth is what gets stored in the TT). Removed; measured as
strength-neutral (‑26 ± … Elo in a 40-game match, i.e. inside the noise) but it makes
the node counts honest. Keep it out unless you re-tune around it.

## 6. `improving` was always false at ply 2

`ss[0].static_eval` was never initialised, so for every node at ply 2 the comparison
`ss[ply].static_eval > ss[ply-2].static_eval` compared against `-MATE_SCORE`, and
`improving` was permanently false. **Fix:** evaluate the root position once at the start
of `search()` and store it in `ss[0].static_eval`.

## 7. `should_stop()` (a clock read) at every single node

```cpp
if (stats.stopped || (tm && tm->should_stop())) { ... }
```

`TimeManager::should_stop()` calls `high_resolution_clock::now()` — do that at 1.5M
nodes/s and you lose a few percent of your nps for nothing. **Fix:** the node limit is
still checked exactly, the wall clock every 256 nodes. Measured **+5 % nps** on `bench`.

## 8. TT: shallower entries could overwrite deeper ones

`storeTT()` for the same position allowed the new entry to replace an existing one that
was up to 4 plies **deeper** (`depth >= entry.depth - 4`), so a depth-0 quiescence entry
could wipe out a depth-4 entry. That throws away information and makes a repeated search
of the same position return a different (usually worse) score. **Fix:** only replace on
`depth >= entry.depth` (or for a PV entry within 2 plies).

## 9. `position … moves` applied unchecked moves

`uci.cpp` called `board.makeMove(move)` for whatever `uciToMove()` returned. A move list
that does not match the position makes `makeMove()` hit undefined behaviour (and an
assert in `chess.hpp`). This is exactly what happened while I was stress-testing with a
buggy harness: a garbage move list corrupted the board and the engine aborted inside
`makeMove`. **Fix:** validate against `movegen::legalmoves()` and stop with
`info string illegal move in position command: …` instead.

## 10. Minor

* `NNUE::evaluate()` returned `i16` while the value is an `int` in centipawns → `i32`.
* Dead code you may want to remove: `probeTT()`, `g_pawnCorrectionHistory`,
  `g_materialCorrectionHistory` (never used), `g_policy_small` (loaded, only used by the
  `policysmall*` debug commands).

## What I checked and found *correct* (so you do not re-investigate these)

* TT mate-score plumbing (`+ply` on store, `-ply` on probe) — correct.
* `see::see_ge()` — matches the reference algorithm (including the "target square stays
  occupied" trick, which is intended), the LVA loop and x-ray updates are right.
* Repetition (`isRepetition(1)` = 2-fold) and 50-move handling, incl. the root.
* Quiescence stand-pat / in-check handling and its TT usage.
* Validation of TT/killer/counter moves against the legal move list.
* Null-move accumulator save/restore, singular-extension depth/verify logic.

## Measurements

`bench` (20 FENs, depth 14):

| build | nodes | nps (3 runs) |
|---|---|---|
| before | 5 175 523 | 1.41 / 1.50 / 1.48 M |
| after | 6 673 710 | 1.48 / 1.57 / 1.54 M |

The node count going *up* is expected: the search no longer applies a random reduction
in PV nodes and no longer shaves a ply off TT-less nodes, so it is less aggressive — but
it is also no longer pruning on undefined behaviour.

Head-to-head, old binary vs new binary, random 8-ply openings, every opening played
with both colours:

| match | games | result | score | Elo |
|---|---|---|---|---|
| `go nodes 20000` (seed 1234) | 24 | 8 W / 6 L / 10 D | 54.2 % | +29 |
| `go nodes 20000` (seed 999) | 60 | 18 W / 13 L / 29 D | 54.2 % | +29 |
| `go movetime 100` (seed 4242) | 24 | 7 W / 5 L / 12 D | 54.2 % | +29 |

So roughly +30 Elo, which is a small number for removing UB — the reason is that the
buggy code was not *always* wrong, it was wrong in a random subset of nodes, and the
rest of the engine is now (correctly) slightly more conservative. The important part is
that the behaviour is now deterministic and debuggable, and that the two crash bugs are
gone.

## Suggested next steps for strength (not done here — they need tuning, not bug fixing)

1. **Re-run SPSA from the fixed build.** All of the pruning margins
   (`RFP_*`, `FUTILITY_*`, `SEE_*_MARGIN`, `lmr_table`) were tuned while LMR decisions
   were random; treat the current numbers as untrusted starting points. Keep
   `RFP`/futility margins as separate `improving`/non-`improving` terms.
2. **LMR table resolution.** `lmr_table[d][m] = int(256 * (0.6037 + ln(d)·ln(m)/2.5755))`
   truncates to whole plies, so reductions below ~1 ply become 0 (depth 1–2 never reduce,
   move 1–2 barely reduce). Store tenths of a ply and keep the comparison in that unit.
3. **TT replacement/aging.** One entry per slot with `depth - 2·age` priority is fragile
   at 256 MB; a 2-way or 4-way bucket (or the classic depth-preferred + always-replace
   pair) would cut the cold-vs-warm score spread I measured (up to ~150 cp on endgames).
4. **Time management.** `MOVE_OVERHEAD_MS = 50` is a lot at fast TC, `movestogo`
   defaults to 30 even without it, and `hard = min(5·base, 0.6·available)` is very
   conservative; `should_continue_depth()` uses `last_depth_ms * 2.5` as the estimate.
5. **PV.** `extractPV()` rebuilds the PV by probing the TT, so the printed PV can
   disagree with `bestmove` (and with what was actually searched). A real triangular PV
   table makes debugging much easier.
6. **One-legal-move case.** `search()` returns immediately with score 0 when there is a
   single legal move; it never reports mate/stalemate scores.
7. Test the policy net separately: `setoption name UsePolicy value false` and re-run a
   match. It influences root LMR and root ordering, so it should pay for itself.
